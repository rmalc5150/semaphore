# Legacy artifact access: owner approved and applied

The user explicitly approved this artifact policy in this session; it has now been applied as the separate `constellation-legacy-artifacts` inline policy. This artifact policy does not grant source-secret access. The later owner-authorized collection launch added separate read grants for the exact shared additional-key secret and existing FDA key secret; see [launch status](../launch/README.md). Automatic approval review rejected the earlier broad S3/source-secret expansion. Before owner approval, the base validation policy was limited to GetObject on three exact immutable public company-universe snapshots. The separate owner-approved artifact policy described below now adds native artifact access; source-secret access remains ungranted.

The approved and applied policy adds read/write access to existing raw records, task checkpoints, collection manifests, source-document evidence and the listed historical progress/queue paths inside the existing research-data prefix. It adds no DeleteObject, source secrets, IAM administration, database credentials or bucket administration. It explicitly denies writes/deletes to the original S3 runtime namespace.

The material risk is that the old task checkpoint names are hashes and do not expose daily versus historical mode in their S3 paths. The required task/watermark permissions can therefore also reach daily task checkpoints. The fixed historical command allowlist, split-mode tests and disabled local historical payloads enforce ownership in application code; IAM alone cannot express the mode boundary in that old layout. Some listed operation paths are shared publication and quota namespaces.

Even with this policy, individual source credentials, Google workload-identity authorization, distributed vendor quotas, publication/notification separation and per-route validation remain gated. Approval of this artifact policy does not enable bulk collection or resume paused sources.
